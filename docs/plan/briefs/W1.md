# W1 brief: data adapters, snapshots, products, tiles, API skeletons

Worktree /Users/natedemoro/Code/Git_Growing-wt/W1, branch `piece/W1`, cut from main after Phase 0. Goal: every live source has a working adapter and a committed snapshot, so the demo never depends on the network. Speed and demo reliability beat architecture.

## Files to create
- `src/lib/data/openMeteo.ts`: forecast (7 days hourly) and historical-forecast fetchers, normalized to hourly records.
- `src/lib/data/nws.ts`: points lookup, then gridpoint mixing height and transport wind, normalized to hourly.
- `src/lib/data/azmet.ts`: latest hourly observation from the nearest Yuma station.
- `src/lib/data/snapshot.ts`: loads `data/snapshots/*.json`; one helper per source that tries live, falls back to the snapshot, and reports which one was used.
- `scripts/fetch-products.ts` writes `data/products.json` (replaces the Phase 0 two-product stub data; keep `src/lib/products.ts` reading it).
- `scripts/snapshot.ts` writes `data/snapshots/open-meteo-forecast.json`, `nws-gridpoint.json`, `azmet.json` (names may vary, keep one file per source).
- `scripts/fetch-tiles.ts` (small, one-time) writes `public/tiles/{z}/{x}/{y}.jpg`.
- `src/app/api/now/route.ts`, `src/app/api/forecast/route.ts`, `src/app/api/station/route.ts`.
- npm scripts in `package.json`: `fetch:products`, `snapshot`, `fetch:tiles` (run with tsx).

## Contract fields used
`src/lib/contract.ts` on main is the authority. Read it first, import from it, never rename or remove a field. If something W1 needs is missing, ask the coordinator before adding it.
- **Product:** name, active ingredient, PubChem CID, vapor pressure in mPa, volatility band (low / moderate / high), illustrative label wind max (mph, flagged "check label"), label minimum DropletClass. Use DropletClass values exactly as `src/lib/droplets.ts` defines them.
- **Site:** tower lat/lon and timezone from `src/lib/site.ts`. No hard-coded coordinates anywhere in W1 code.
- **Hourly record** (the normalized shape W3's derive and W5 consume): time, 2 m temp, 80 m temp (plus 120/180 m if present), 10 m and 80 m wind speed and direction, gusts, RH, dew point, cloud cover, precipitation and probability, surface pressure, boundary layer height, is_day. If contract.ts defines this type, use it; if not, define it in `src/lib/data/` as W1-internal and tell the coordinator.
- **API responses:** each carries the payload plus data timestamp, source names, and a `source` flag of live or snapshot (what the "cached data" chip reads).

## Verified API facts (existing-structure.md, 2026-11-15)
- **Open-Meteo forecast:** `api.open-meteo.com/v1/forecast`, no key, 8 days hourly. Temperature at 2/80/120/180 m, wind at 10/80/120/180 m, gusts, RH, dew point, boundary_layer_height, cloud_cover, precipitation and probability, surface pressure, is_day. 180 m fields are null for the last 6 hours, so treat them as optional. Units selectable.
- **Open-Meteo historical:** `historical-forecast-api.open-meteo.com/v1/forecast`, 2024-01-01 to 2026-11-01, all multi-height fields non-null. W1 only provides the fetcher; W3 runs calibration with it.
- **NWS:** `api.weather.gov`, User-Agent header required. Use a generic one such as "spray-or-wait-hackathon"; never a personal email. Gridpoint fields: mixingHeight (m), transportWindSpeed (km/h), transportWindDirection, twentyFootWindSpeed (km/h). dispersionIndex is empty, skip it. The Willcox probe returned TWC; Yuma will be a different office, so always use the points lookup, never a hard-coded grid.
- **AZMet:** `api.azmet.arizona.edu/v1/observations/hourly/<station>/<start>/<duration>`. Yuma stations az02 Yuma Valley, az14 Yuma N.Gila, az36 Yuma South (nearest likely az36). Fields are strings: temp_airF, relative_humidity, dwptF, wind_spd_mph, wind_vector_dir, wind_spd_max_mph.
- **PubChem:** `pubchem.ncbi.nlm.nih.gov/rest/pug_view/data/compound/<CID>/JSON?heading=Vapor+Pressure`. Returns free-text strings (chlorpyrifos CID 2730: 2.02e-5 mmHg at 25 C).

## Risks and fallbacks
- **Site pin lands after W1 fetches.** Use 32.61, -114.64, re-run snapshot and tiles after the pin (step 11). Coordinates are only ever read from site.ts.
- **Upstream down or slow on stage.** Short timeouts, silent snapshot fallback, `source` flag in every response. Snapshots must exist before the routes ship.
- **AZMet down or station stale.** Try az36, az02, az14; else snapshot. Cut order lists the AZMet reading first, so do not sink time here.
- **NWS 500s or slow (common).** Retry once, then snapshot; the overlay is context only and second in the cut order.
- **PubChem text unparseable.** Hand-enter the value with a note; never block the product file on parsing.
- **Tile count blows past 400 or Esri throttles.** Drop zoom 17 outside the farm; throttle; skip existing files. W7 keeps the live Esri URL as fallback.
- **Vercel bundling of snapshots.** Import the JSON statically (not runtime fs reads of arbitrary paths) so it ships with the serverless function.
- **Route caching.** Mark the routes dynamic so `/api/now` is not frozen at build time.
- **Lockfile conflicts.** Expected; take main's lockfile and re-run npm install (plan section 9).
