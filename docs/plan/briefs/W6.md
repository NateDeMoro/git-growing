## Ordered steps
1. FrameProvider: Live mode polls `/api/now` every 60 s. Simulate mode fetches `/sim/week.json` once (a static file, so zero network beyond the page's own origin, and no external call) and drives a playhead at 0.25, 1 and 6 sim-hours per second. Expose current frame, mode, playhead, speed, beats, cached flag and setters. Default to Simulate if the live fetch fails.
2. Assessment hook: takes the current frame and selected product, runs assess in full mode (with droplet recommendation) and single-station mode. Memoize by frame index (or frame time) plus product id with a small cache, so re-renders and the 3D animation loop never re-run it. Pass the assessment to every panel and to Scene3D.
3. Station card: our 5 ft data in single-station mode, next to the AZMet reading from `/api/station` also run in single-station mode. In Simulate, show only our 5 ft single-station result (AZMet is live-only). If AZMet fails, use the snapshot and show the chip.
4. Logging through `src/lib/log.ts`: append on every status change, and once per sim-hour boundary in Simulate or once per live poll. Mode is live or sim. Include the droplet recommendation. Key dedupe on frame time so seeking backward or replaying does not double-log the same sim-hour twice in one pass.
5. Playback bar: beat markers on the scrubber from week.json, "next beat" and jump-to-beat. Seeking sets the playhead directly.
6. DemoPanel hotkeys (backtick toggles panel; hotkeys work with it hidden): 1 to 6 jump to Beats A to F, space pause, [ and ] speed, R clear log, F overview camera, V 2D/3D, L Live/Simulate. Camera keys call the Scene3D API W7 exposes; ignore keys while focus is in an input.
7. Early-warning banner: in Simulate, read the look-ahead field and show "storm arriving in N hours" (or the generic worsening text) when the status 3 sim-hours ahead is worse. In Live, use W5's early warning from the forecast.
8. Forecast tab: fetch `/api/forecast`, run W5's forecast helpers client-side with the selected product, memoize per product. Feed ForecastStrip, NextWindowCard, WindowDial and the chart.
9. "Cached data" chip whenever any response says cached. "Why these limits" panel lists every rule from thresholds.ts with cutoff, kind (heuristic rows labeled "heuristic, tunable") and source link.
10. Write the integration test, run `npm test` and `npm run build` in the background, run `npm run dev` and check Beat A and Beat F by hand, stop the dev server, commit.

## Risks
- Performance: 6 sim-hours per second at 5-minute frames is 72 frames per second, and the droplet recommendation runs assess up to eight times per frame, plus single-station, so roughly 650 calls a second. Memoize per frame and product, advance the React playhead at most about 30 times a second (skip intermediate frames, but still evaluate skipped frames for status-change logging), and keep assess out of the 3D animation loop. Profile once in Chrome at 6x.
- Skipped frames can hide a status change. The logger must scan every frame between the last and current playhead, using the memoized assess, so the log and the "same changes on replay" check stay deterministic.
- Product change mid-playback must clear the memo cache for the old product, or the status lags.
- Zero-network Simulate: no fetch to /api/* or any external host in Simulate. Verify with `npm run build && npm run start` and the browser offline.
- localStorage can throw; rely on log.ts's memory fallback, do not access storage directly.
- Contract drift from W5 or W7: if a field you need is missing, ask the coordinator; do not invent local copies of types.
- Lockfile conflicts on rebase: take main's lockfile and re-run npm install, per plan section 9.
