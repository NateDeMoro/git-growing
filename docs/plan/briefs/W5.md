## Contract fields used
Read `src/lib/contract.ts` on main first and use its names exactly. Never rename or remove a field. If something below has no field, ask the coordinator before adding one (add only).
- SceneFrame: time, layers (height, temperature, wind speed, wind direction), the derived summary (inversion °F, speed shear, direction shear, Delta T, RH), cloud, rain rate, gusts, pressure and pressure history, sun elevation.
- Assessment: status, reasons, recommended droplet class.
- Reason: rule id, status, text, source tag.
- Status ordering (GO < CAUTION < STOP), from the contract or engine helper; do not redefine it.
- ForecastWindow: start, end, status, and top reason if the type has one.
- Product: volatility band (for the vapor caution).

## Ordered steps
1. Read contract.ts, the assess signature, derive's input record shape and the W1 adapters. Note how the engine takes the "inversion forecast within 12 hours" input (the plan puts the vapor CAUTION in the engine). If assess has no such input, ask the coordinator which side owns it before writing code.
2. forecast.ts, pure functions taking already-fetched data (no fetch inside, so tests need no network):
   - Derive one frame per forecast hour through derive.ts with the committed calibration.
   - Compute the vapor-caution input per hour: true when any hour in the next 12 has inversion above 0. Pass it to assess only for high-volatility products.
   - Assess each frame with the given product in full mode.
   - Merge consecutive same-status hours into ForecastWindow entries.
   - Next GO window: the first window with status GO lasting at least 2 hours, or none.
   - Early warning: the first hour within the next 6 whose status is worse than hour 0, with its top reason and hours-ahead count. Return none if nothing worsens.
   - Overlay: attach NWS mixing height and transport wind per hour when present, as context only, never fed to assess.
3. `/api/forecast?offline=0|1`: fetch Open-Meteo 7-day and NWS through W1 adapters, fall back to snapshots on failure or offline=1. Return derived hourly frames, the overlay, source names, data timestamp and a cached flag. Assessment stays on the client, per plan 5c. Export the forecast.ts helpers so W6 can run them client-side.
4. `/api/now?offline=0|1`: pick the current hour (America/Phoenix) from the same Open-Meteo data, derive the frame, and apply a small seeded wobble keyed to the current minute (deterministic hash of the minute, no Math.random) to temperatures and winds at each layer. Keep the wobble well under rule cutoffs (for example a few tenths of a degree, under 0.5 mph) so it never flips a status by itself. Return the frame, source names, data timestamp, and cached true when a snapshot was used.
5. `/api/station?offline=0|1`: the latest AZMet reading from the nearest station (az36 unless W1 chose otherwise), normalized, with snapshot fallback and the cached flag.
6. Write tests, run `npm test` and `npm run build` in the background, fix, commit.

## Tests (`tests/forecast.test.ts`, synthetic frames or assessments, no network)
- Consecutive same-status hours merge into windows with the right start and end.
- The next safe window skips a 1-hour GO and picks the first GO of 2 hours or more.
- The early warning picks the first worsening hour within 6 hours, ignores a worsening at hour 7, and returns none when nothing worsens.
- Optional if cheap: the vapor input turns on for a high-volatility product when an inversion is 10 hours out and stays off at 13 hours.

## Risks
- Engine input mismatch for the 12-hour vapor caution. Resolve in step 1, do not fork rule logic into forecast.ts.
- Timezone: Phoenix has no DST, but Open-Meteo hours must be requested or parsed as America/Phoenix, or "current hour" is off by 7.
- Wobble must be deterministic per minute and must not cross a cutoff. Clamp it.
- The snapshot forecast is dated today. "Next 6 hours" and "current hour" must be measured from the data's first hour when the snapshot is stale, not from wall clock, or the forecast tab goes empty during the demo.
- Performance: 168 hours times eight droplet classes is about 1,300 assess calls per product. Fine server-side or client-side once. W6 should memoize the result per product so it does not rerun on every render.
- Route caching: set the routes dynamic (no static prerender) so `/api/now` is not frozen at build time on Vercel.
- Lockfile conflicts on rebase: take main's lockfile and re-run npm install, per plan section 9.
